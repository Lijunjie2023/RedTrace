# 线上登录恢复记录

日期：2026-08-07

## 故障与根因

- 线上前端能够打开，但会话接口经 Nginx 返回 502。
- `readtrace-api.service` 处于反复重启状态，API 没有监听 `127.0.0.1:3100`。
- 当时线上代码要求正式模式管理员密码至少 16 位，而本地配置值不满足该门槛，运行时配置校验失败。服务入口没有记录安全的启动错误信息，导致 systemd 日志只显示退出码。
- 登录页此前把服务连接失败统一显示为账号或密码错误，掩盖了实际服务故障；该提示已在本次部署代码中区分处理。

## 恢复操作

- 管理员账号和密码只从本地 `.env.local` 在进程内读取，通过 SSH 标准输入传输。
- 线上 `/etc/readtrace/readtrace.env` 只更新 `ADMIN_USERNAME` 和 `ADMIN_PASSWORD`，其他配置保持不变；更新使用同目录临时文件和原子替换，并保持 `0640 root:readtrace` 权限。
- 本地 `.env.local` 补齐线上 API 代理目标和自签名证书开发代理设置，没有把配置文件或凭据纳入 Git。
- 为旧部署提交创建 Git 回滚分支，并保留更新前静态页面副本。
- ECS 部署兼容提交 `18f2cb0`，随后发生的并发提交 `4dd4df0` 以 `18f2cb0` 为直接父提交，因此没有覆盖认证兼容修复。本次恢复没有回退或覆盖并发提交。
- 首次安装因 ECS 内存不足被终止。核对磁盘和现有交换空间后，在固定路径创建 2GB 临时交换文件，没有修改 `/etc/fstab`。
- 并发部署的新自动分析定时任务在部署后立即触发，引发系统 OOM。内核记录显示分析进程被终止，API 随后也两次以状态 137 退出并造成 502。已经停用并禁用 `readtrace-analysis.timer`，不影响已有业务数据；API 恢复后持续观察并重新验证登录。
- 临时交换文件在首次清理后暴露出机器的持续内存压力，因此已经按原固定路径重新启用并暂时保留。后续需要在扩大机器内存、降低同机负载或配置正式交换空间后，再受控停用并删除。

## 后续注意事项

- ECS 仍使用 Node.js 20.20.0，依赖 `cookie@2.0.1` 声明要求 Node.js 22。当前测试、构建和线上登录均通过，但后续需要单独规划不影响同机其他服务的 Node.js 22 升级。
- `npm ci` 仍报告两项高严重度依赖告警。当前沿用已有风险记录，没有执行可能引入破坏性升级的自动修复。
- 本地代理配置已经补齐，但检查时本地 Vite 服务没有运行；重新启动本地前端后才会读取新的代理配置。
- `/var/tmp/readtrace-deploy.swap` 当前仍作为临时交换空间启用，未写入 `/etc/fstab`。服务器现有交换空间长期接近满载，不能在没有扩容或减负方案时再次直接执行 `swapoff`。
