# MySQL 舆情概览聚合实现

日期：2026-08-06

## 背景

正式数据模式下的 `GET /api/v1/overview` 由 `MysqlRepository.getOverview` 直接抛出 `DATA_NOT_READY`，导致已完成数据库连接和采集后，概览页仍然显示“数据请求失败”。

## 本次实现

- 按品牌筛选读取采集任务状态；没有成功或部分成功任务时，按接口契约返回 `NOT_COLLECTED`、空数组和 `null` 指标。
- 使用 MySQL 8 公共表表达式统一帖子与评论的有效分析口径。最新成功模型结果作为基础，未删除的人工修正覆盖对应字段。
- 聚合帖子数、评论数、负面数量、负面比例、情感日趋势、品牌排行、品类排行、问题类型排行和主题证据数量。
- 高风险内容从真实帖子和评论中选择，并复用现有内容摘要映射，保留原始证据链接和有效分析。
- 评论表只有不可验证的展示时间文本，因此概览的时间筛选和趋势分桶按评论所属帖子的发布时间计算，避免把采集时间误当成评论发布时间。
- 当前没有稳定的对比周期定义，主题变化比例返回契约允许的 `null`，不生成虚构环比。

## 边界说明

- 最近终态任务失败时返回 `FAILED`，部分成功时返回 `PARTIAL`，成功时返回 `HEALTHY`。
- `STALE` 需要产品定义过期阈值后再实现，本次不自行假设阈值。
- 筛选范围内没有内容、但品牌已经成功采集时，计数返回 `0`；只有尚未成功采集时计数才返回 `null`。

## 真实环境修正

- 首次在真实 MySQL 8 执行时，窗口函数结果别名 `row_number` 被解析为保留关键字并触发 `ER_PARSE_ERROR`。
- 别名已改为 `analysis_rank`，不改变排序和最新分析选择逻辑。
- 第二次真实执行发现人工修正 JSON 的 `utf8mb4_bin` 与分析枚举字段的 `ascii_bin` 在 `CASE` 中发生排序规则冲突。
- 情感、风险等级和内容类型现已显式统一为 `ascii_bin`；人工修正的品类编号在确认是有效的 `BIGINT UNSIGNED` 十进制文本后才转换，空值、非数字和越界值统一按无品类处理。

## 小规格 RDS 性能约束

- 采集健康状态不再读取完整任务历史，改为两个按任务时间倒序且带 `LIMIT 1` 的查询，分别读取最后一次成功采集和最近终态。
- 概览公共表表达式先建立当前日期与品牌筛选范围内的帖子和评论，再通过帖子、评论外键索引缩小 `analysis_records` 候选，窗口函数只为当前范围选择最新分析。
- 七条概览聚合查询按 `2 + 2 + 2 + 1` 分组执行，最大同时执行两条重聚合查询，以适配 1 核 2 GB RDS。
- 高风险证据详情按实际命中的内容类型补充查询；没有高风险内容时不会产生详情查询。
